# RAG复习总结

RAG 全称是 **Retrieval-Augmented Generation，检索增强生成**。你可以先记住一句最核心的话：

> **RAG = 先从外部知识库里找资料，再把找到的资料交给 LLM，让 LLM 基于这些资料回答。**

它解决的是一个非常现实的问题：**LLM 参数里不可能记住所有知识，而且参数里的知识可能过时，也不知道你的私人文档。**

比如你问普通 ChatGPT：

> “ XXX书里YYY内容讲的是什么？”

模型如果没见过这本书，只能凭训练数据回答，甚至可能幻觉。

而 RAG 的流程是：

**问题 → 搜索你的 《XXX》 数据库/PDF → 找到YYY相关段落 → 把这些段落连同问题一起交给 LLM → LLM 根据原文回答。**

这就是 RAG。

------

# 一、RAG的作用

我们之前讲 Transformer、GPT 时，你已经知道：

```
输入 Token
   ↓
Embedding
   ↓
Transformer Decoder
   ↓
Hidden State
   ↓
LM Head
   ↓
预测下一个 Token
```

LLM 的知识主要储存在模型参数中。

例如：

```
GPT
参数：
Wq
Wk
Wv
FFN 权重
Embedding
...
```

训练过程中：

```
大量互联网文本
      ↓
预训练
      ↓
模型参数发生变化
      ↓
知识被“压缩”进参数
```

问题来了。

如果今天你有一篇刚发表的论文：

```
XXX.pdf
```

GPT 训练的时候根本没见过。

那么：

```
用户：
XXX中的模型 使用了什么视觉对齐方法？

GPT：
？？？
```

LLM 本身不知道。

传统方法之一是：

```
重新训练 / Fine-tuning
```

但是成本太高。

于是 RAG 的思路非常简单：

```
不用重新训练模型

只需要在回答前

先查资料
```

于是系统变成：

```
             外部知识库
                 ↑
                 │ 检索
用户问题 ─────────┘
   │
   ↓
问题 + 检索资料
   │
   ↓
LLM
   │
   ↓
答案
```

所以你可以把 RAG 理解成：

> **给 LLM 配一个“可以翻资料的图书馆”。**
>
> **拿到问题后先检索再生成，然后把问题和检索到的topk个资料一起发给LLM**

------

# 二、RAG 的核心结构

一个标准 RAG 实际上分成两个阶段：

```
阶段 A：构建知识库    - 外部数据DB -> chunk ->  vectorDB
阶段 B：用户提问      - 问题 -> vector +-> Top-k vectorDB -> llm
```

即

>**1.离线建立向量知识库**
>
>  将 Pdf, word 等文档解析，分块chunk, 再经过 Embedding 模型转换成向量，将向量加入FAISS索引，同时保存向量ID 和 原始文本之间的映射。
>
>**2.在线检索与回答**
>
>用户输入问题后，使用相同的 Embedding 模型 将问题向量化，通过 FAISS 检索最相似的 Top-K 个结果，再根据ID找回原始文本，交给LLM生成答案。

完整流程：

```
                构建阶段

PDF / Word / 网页 / 数据库
          │
          ↓
       文本提取
          │
          ↓
       文本切块
        Chunk
          │
          ↓
    Embedding Model
          │
          ↓
       向量
          │
          ↓
      Vector DB
      向量数据库


                查询阶段

用户问题
   │
   ↓
Embedding
   │
   ↓
问题向量
   │
   ↓
Vector DB 检索
   │
   ↓
Top-K 文档
   │
   ↓
问题 + 文档
   │
   ↓
LLM
   │
   ↓
最终回答
```

这里面最关键的是三个东西：

```
Embedding
Vector Database
LLM
```

# 四、Chunk 文本切块

这是 RAG 非常重要的一步。

假设有一本 500 页的书。

不可能每次用户提问都：

```
把整本书 30 万字
全部塞给 GPT
```

所以需要切块。

例如原文：

```
第1章 XXX
......
第2章 YYY
......
第3章 ZZZ
......
```

可以切成：

```
Chunk 1
第1章的一部分

Chunk 2
第1章另一部分

Chunk 3
...

Chunk 4
...

Chunk 5
...

Chunk 6
...
```

例如：

```
chunk_size = 500  chunk_overlap = 100
```

意思：

```
Chunk1：
第 0 ~ 500 字

Chunk2：
第 400 ~ 900 字

Chunk3：
第 800 ~ 1300 字
```

注意这里有：

```
overlap = 100
```

即相邻文本块重复一部分。

为什么？

假设一句话正好被切开：

```
Chunk1：

海参具有滋阴补肾、增强免疫、

---------------------

Chunk2：

抗疲劳等功效。
```

如果没有 overlap：

```
增强免疫

和

抗疲劳
```

上下文可能断掉。

有 overlap：

```
Chunk1：
海参具有滋阴补肾、增强免疫、抗疲劳

Chunk2：
增强免疫、抗疲劳等功效，同时……
```

语义会更完整。

# 五、Embedding模型 - 语义搜索

## Embedding模型

这里就是你之前学过的 **词嵌入 Embedding** 思想的进一步应用。

你之前学 Transformer 时有：

```
nn.Embedding(vocab_size, embed_dim)
```

作用是：

```
Token ID
   ↓
向量
```

例如：

```
猫
↓
[0.23, -0.81, 0.42, ...]

狗
↓
[0.21, -0.75, 0.39, ...]
```

因为猫和狗语义接近，所以两个向量距离也比较近。

RAG 里面也一样。

但这里一般不是：

```
word → vector
```

而是：

```
一句话 / 一段文本
        ↓
Embedding Model
        ↓
一个向量
```

例如：

```
海参具有滋阴补肾作用
```

经过 Embedding Model：

```
[0.12,
 0.71,
 -0.33,
 ...
 0.28]
```

可能是：

```
768维
1024维
1536维
3072维
```

取决于 embedding 模型。

**于是每个 Chunk 都变成一个向量：**

```
Chunk1 → vector1
Chunk2 → vector2
Chunk3 → vector3
Chunk4 → vector4
...
```

## 语义搜索

这个地方非常关键。

假设：

```
文本 A：
海参具有补肾作用

文本 B：
海参可以改善肾虚症状

文本 C：
鲸鱼生活在海洋中
```

Embedding 后：

```
A → [......]

B → [......]

C → [......]
```

虽然 A 和 B 的文字并不完全一样：

```
补肾
≠
改善肾虚症状
```

但它们的**语义接近**。

所以：

```
vector(A)
≈
vector(B)
```

而：

```
vector(A)
和
vector(C)
```

距离比较远。

于是我们就能实现：

> **语义搜索。**

而不是传统数据库：

```
WHERE text LIKE '%补肾%'
```

传统关键词搜索可能找不到：

```
改善肾虚
```

但 Embedding 可以找到。

这正是 RAG 强大的地方。

# 六、Vector Database 向量数据库

假设一本书被切成：

```
10,000 个 Chunk
```

每个 Chunk 都有：

```
文本
+
Embedding Vector
```

例如：

```
ID: 001

text:
海参具有滋阴补肾作用

vector:
[0.12, 0.72, -0.31, ...]
```

我们就需要一个数据库保存这些东西。

这就是：

> **Vector Database，向量数据库。**

常见的有：

```
FAISS
Chroma
Milvus
Qdrant
Pinecone
Weaviate
```

> FAISS（检索相似向量）:  **Meta 开源的向量相似度检索库，作用是从大量向量中，找出与查询向量最相似的 Top-K 个向量。**
>
> FAISS 的本质是 最近邻搜索（Nearest Neighbor Search）。
>
> 它主要用于 RAG（检索增强生成）、语义搜索、推荐系统、图像检索等场景。
>
> FAISS 的底层主要由 C++ 实现，提供 Python 接口，并支持部分 GPU 加速索引。
>
> 主要工作：面对10万甚至100万个向量，怎样快速找出与查询向量最相似的top-k个向量。
>
> **Embedding 负责表示语义，FAISS 负责高效寻找相似内容，LLM 负责理解上下文并组织答案。**

# 七、整合LLM Prompt

这一步才真正轮到 LLM。

假设检索出了：

```
文档1：
海参性温，具有补肾、健脾作用。

文档2：
海参汤用于身体虚弱、休息痢等。

文档3：
海参含丰富蛋白质及多种矿物元素。
```

系统会构造 Prompt：

```
你是一名海洋药物助手。

请根据以下资料回答用户问题。
如果资料中没有答案，请明确说明。

资料：

[1]
海参性温，具有补肾、健脾作用。

[2]
海参汤用于身体虚弱、休息痢等。

[3]
海参含丰富蛋白质及多种矿物元素。

用户问题：

海参有哪些补益作用？
```

然后整个东西：

```
Prompt
 ↓
LLM
 ↓
Answer
```

LLM 输出：

```
根据提供资料，海参主要具有补肾、健脾等补益作用，
并可用于身体虚弱等情况。
```

所以你一定要分清楚：

```
Embedding Model
负责：找资料

LLM
负责：读资料 + 组织语言 + 回答
```

这两个模型不是一回事。

# 八、RAG 和 Fine-tuning 有什么区别？

这是一个非常经典的问题。

假设你有自己的专业知识：

```
海洋药物数据库
```

Fine-tuning 思路：

```
知识
 ↓
训练
 ↓
改变模型参数
```

RAG：

```
知识
 ↓
数据库
 ↓
回答时检索
```

也就是说：

```
Fine-tuning：
把知识学进脑子

RAG：
考试时查书
```

**它们解决的问题也不同。**

Fine-tuning 更适合：

```
改变模型行为
改变回答风格
学习特定任务
学习固定输出格式
```

例如：

```
输入一篇医学记录
→ 必须输出固定 JSON
```

而 RAG 更适合：

```
让模型知道大量外部知识
```

比如：

```
公司内部文档
论文数据库
药物数据库
法律法规
产品手册
个人笔记
```

所以实际项目中经常是：

```
RAG + Fine-tuning
```

而不是二选一。

## 1. Query Rewrite

Query Rewrite（查询重写）:把用户提出的问题，转换成更适合检索系统理解和搜索的查询

假设我们正在构建一个海洋药物文献 RAG 系统。

用户输入：

> 有哪些海洋里的东西能抗癌？

对于人类来说，很容易理解这个问题。但直接拿它进行检索，可能存在几个问题：

- “海洋里的东西”过于口语化，缺乏专业术语。
- “抗癌”可能在文献中被表述为“抗肿瘤活性”。
- 没有明确要检索药物、天然产物还是化合物。

因此，我们可以利用 LLM 将其重写为：

> 检索具有抗肿瘤活性的海洋来源天然产物、海洋药物及相关化合物，重点关注其抗肿瘤作用和药理活性。

重写前后对比：

|          | 用户原始问题 | 重写后的问题             |
| -------- | ------------ | ------------------------ |
| 语言     | 口语化       | 专业化                   |
| 关键词   | 海洋、抗癌   | 海洋天然产物、抗肿瘤活性 |
| 表达     | 模糊         | 更明确                   |
| 检索效果 | 可能遗漏文献 | 更容易匹配专业文献       |

这里的关键是：Query Rewrite 不负责直接回答问题，而是生成更适合检索的查询。

### 工作流程

<img src="assets/image-20261011171343685.png" alt="image-20261011171343685" style="zoom:67%;" />

整个过程可以理解为：

**用户提问 → LLM 重写问题 → 检索相关文档 → 文档排序 → LLM 生成答案。**

其中，Query Rewrite 通常由一个 LLM 完成，也可以使用规则、词典或者专门训练的小模型。

## 2. Hybrid Search

​          Hybrid Search（混合检索）= 关键词检索（Sparse Search）+ 语义向量检索（Dense Search）

它将两种检索方式结合起来，既能准确匹配关键词，又能理解用户问题的语义，从而提高检索结果的准确性和召回率。

假设我们正在开发一个医学文献 RAG 系统，数据库中有这样一段文本：

> 阿司匹林具有解热、镇痛及抗炎作用，可通过抑制环氧化酶减少前列腺素的合成。

用户提出问题：

“哪些药物可以缓解疼痛？”

我们来比较两种检索方式。

>1. **关键词检索（BM25）**
>
>   主要根据查询词与文档中的词汇匹配程度进行评分。
>
>   用户问的是“缓解疼痛”，但文档写的是“镇痛”。如果没有词汇扩展等处理，可能无法很好地匹配。
>
>   优点：匹配专有名词、药物名称、编号和精确术语特别有效。

> 2. **语义检索（Embedding + FAISS）**
>
>    通过 Embedding 模型将问题和文档转换成向量，再计算向量相似度。
>
>    模型可能理解“缓解疼痛”与“镇痛”表达的是相近含义，因此可以找到该文档。
>
>    优点：能够匹配同义词、近义表达以及语义相近的文本。

但是语义检索也有缺点。例如用户要找特定编号的化合物 `CAS 50-78-2`，纯向量检索不一定能精确区分相似编号。

这种东西没有什么“语义”。

它是一个精确字符串。

Embedding Search 可能反而不好。

因此，我们希望同时利用两种方法的优势。

所以现代 RAG 很喜欢：

```
Hybrid Search
```

即：

```
Dense Search（Embedding + FAISS）  +  Keyword Search（BM25）
```

### 工作流程

<img src="assets/image-20261011170253184.png" alt="image-20261011170253184" style="zoom: 67%;" />

具体流程是：

1. 并行检索：BM25 根据关键词检索 Top-K 文档；FAISS 根据向量相似度检索 Top-K 文档。
2. 结果融合（Fusion）：合并两路结果并去重，计算综合排名。
3. 重排序（Rerank，可选）：利用更精确的模型重新评估文档与问题的相关性。
4. 生成答案：选择排名靠前的文档放入 LLM 上下文，生成最终回答。

注意：Hybrid Search 本身主要负责检索与融合，Reranker 和 LLM 是后续可选或独立的环节。

### 结果融合

这是 Hybrid Search 最关键的部分。

假设两种方式分别检索到以下结果：

| 文档   | BM25 排名 | 向量检索排名 |
| ------ | --------- | ------------ |
| 文档 A | 1         | 3            |
| 文档 B | 3         | 1            |
| 文档 C | 2         | 未命中       |
| 文档 D | 未命中    | 2            |

现在问题来了：如何将两份排名合并成一份？

最经典的方法之一是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**。

其公式为：
$$
 \mathrm{RRF}(d)=\sum_{i=1}^{m}\frac{1}{k+\mathrm{rank}_i(d)} 
$$
其中：

- \(\mathrm{rank}_i(d)\)：文档 \(d\) 在第 \(i\) 路检索中的排名。
- \(k\)：平滑常数，通常取 60。
- \(m\)：检索方法的数量，这里为 2。
- 未出现在某一路检索结果中的文档，不从该路获得分数。

例如文档 A：
$$
 \mathrm{RRF}(A)=\frac{1}{60+1}+\frac{1}{60+3} \approx0.03226 
$$

## 3、Reranker

Reranker（重排序模型） ：先粗排召回，再精排筛选

即：Retriever 负责粗筛，Reranker 负责精排

假设我们正在开发一个海洋药物 RAG 系统。

用户提问：

> 海参有哪些药用禁忌？

经过 Hybrid Search，系统找到了以下四个文档片段：

| 初始排名 | 文档内容                         | 实际相关性 |
| -------- | -------------------------------- | ---------- |
| 1        | 海参具有补肾益精、养血润燥等作用 | 一般       |
| 2        | 海参含有蛋白质、多糖等营养成分   | 较低       |
| 3        | 海参性温，脾虚多痰、便溏者应慎用 | 很高       |
| 4        | 海参广泛分布于我国沿海地区       | 很低       |

可以看到，Hybrid Search 虽然成功找到了相关文档，但排名并不理想。

因为 BM25 和向量检索主要擅长快速召回候选内容，其评分不一定能够充分判断文档是否真正回答了用户的问题。

这时就需要 Reranker。

它会对每一个候选文档重新评分：

- **Reranker 重新评分后的排名（示意分数）**

1.海参的药用禁忌           	 0.97

2.海参的药理作用  		 0.48

3.海参的营养成分 		  0.19

4.海参的地理分布 		  0.05



原本排在第三的文档，现在被提升到了第一。

这样，后续 LLM 就能够优先读取真正相关的资料。

### 核心原理

要理解 Reranker，首先需要区分两种模型架构：

>  **Bi-Encoder（双编码器） 和 Cross-Encoder（交叉编码器）。**

### 1. Bi-Encoder：向量检索常用的架构

之前我们学习的 Embedding + FAISS，就属于典型的双编码器检索方案。

它将 Query 和 Document 分别编码：

<img src="assets/image-20261011172831294.png" alt="image-20261011172831294" style="zoom:50%;" />

其数学表示为：
$$
\mathbf q=f(Q),\qquad \mathbf d=f(D)
$$

$$
 S(Q,D)=\frac{\mathbf q\cdot\mathbf d}{\|\mathbf q\|\|\mathbf d\|} 
$$

其中：

- Q：用户查询。
- D：文档。
- f：Embedding 编码模型。
- S：语义相似度分数。

它的最大优势是：文档向量可以提前计算并建立索引，查询时只需要编码 Query，再快速搜索相似向量。

但是 Query 和 Document 在编码阶段是彼此独立的，缺少直接的跨文本交互。

### 2. Cross-Encoder：经典 Reranker 架构

​         Cross-Encoder 不会分别生成两个向量，再计算它们的余弦相似度。

相反，它会将 Query 和 Hybrid Search 输出的 Document 拼接在一起，送入同一个 Transformer 模型。

<img src="assets/image-20261011173152956.png" alt="image-20261011173152956" style="zoom:50%;" />

例如输入：

```
[CLS] 海参有哪些药用禁忌？ [SEP]
海参性温，脾虚多痰、便溏者应慎用。 [SEP]
```

Cross-Encoder 中的自注意力机制，可以直接建立两段文本之间的 Token 级别交互关系。

例如模型可以学习：

- “海参”对应文档中的“海参”。
- “禁忌”与“不宜使用”“慎用”等表达密切相关。
- 文档讨论的是用药限制，而不只是普通的药理作用。

模型最终输出一个相关性分数：
$$
 S(Q,D)=f_{\theta}(Q,D) 
$$
在采用 CLS 池化的典型架构中，可以表示为：
$$
 h=\operatorname{Transformer}([Q;D])_{\mathrm{CLS}}
$$

$$
 S(Q,D)=W h+b
$$

这里的 W, b 是可训练的评分头参数。

需要注意，具体模型可能采用不同的输入模板和池化方式，并非所有 Reranker 都使用 CLS。

这就是 Cross-Encoder 与普通 Embedding 检索的本质区别：前者直接建模 Query 与 Document 的交互，后者通常比较两个独立生成的向量。

# 十八、Metadata

Metadata（元数据）: 描述、组织、过滤和追溯知识库中的文档。

假设我们正在构建一个海洋药物文献 RAG 系统，知识库中存储着这样一段文本：

> 海参具有补肾益精、养血润燥等作用，主要含有海参多糖、海参皂苷等活性成分。

这段文本就是 Content（正文内容）。

而这段文本还可以附带以下信息：

```
{
  "document_id": "doc_001",
  "chunk_id": "chunk_001",
  "source": "海洋药物与效方.pdf",
  "page": 128,
  "drug_name": "海参",
  "category": "海洋动物药",
  "section": "药理作用"
}
```

这份 JSON 就是 Metadata。

它告诉我们：

- 这段文本来自哪本书。
- 位于书中的哪一页。
- 属于哪种药物。
- 具体属于哪个章节。
- 对应哪个文档和文本片段。

因此，Metadata 并不是需要模型回答的正文，而是用来描述正文的结构化信息。

### 作用

### Metadata Filtering（元数据过滤）

假设用户提问：

> 查找《海洋药物与效方》中有关海参药理作用的内容。

如果不使用 Metadata，系统可能直接通过 Embedding + FAISS 检索整个知识库。

但这可能检索到其他书籍中关于海参的内容，甚至其他药物的相似描述。

使用 Metadata Filtering 后，我们可以先添加过滤条件：

```
filters = {    "source": "海洋药物与效方.pdf",    "drug_name": "海参",    "section": "药理作用"}
```

系统只在满足这些条件的文档片段中进行搜索。

<img src="assets/image-20261011174208022.png" alt="image-20261011174208022" style="zoom:50%;" />

这里的关键区别是：

- Metadata Filtering：筛选满足明确属性条件的文档。
- Semantic Search：寻找语义相近的文档。
- Reranker：判断候选文档与问题的实际相关程度。

注意，Metadata Filtering 可以在检索前、检索过程中或者检索后执行，具体取决于数据库的实现。上图展示的是预过滤方案。

# 十九、Chunk Size 设置

假设 Chunk 太小：

```
50 token
```

可能变成：

```
海参性温。

下一 Chunk：

具有补肾作用。

下一 Chunk：

适用于身体虚弱。
```

上下文破碎。

如果 Chunk 太大：

```
5000 token
```

里面可能同时包含：

```
海参
海马
海藻
牡蛎
海带
```

Embedding 会变得：

```
语义不集中
```

于是检索质量下降。

所以 RAG 有一个核心思想：

> **Chunk 应当是一个语义相对完整的知识单元。**

不一定机械地：

```
每500字切一次
```

更好的方法是：

```
按标题
按段落
按章节
按语义
```

比如你的书：

```
药物
 ├─ 来源
 ├─ 别名
 ├─ 性味
 ├─ 功效
 ├─ 主治
 └─ 效方
```

就可以直接：

```
一个效方 = 一个 Chunk
```

甚至效果可能比固定字数切块好很多。

# 二十、数据工程

RAG 有一句非常重要的话：

> **Garbage in, garbage out.**
>
> （垃圾输入，垃圾输出。如果输入的数据质量差、不准确或包含错误，那么即使模型再强大，也难以生成高质量、可靠的结果。）

如果 Retriever 找错文档：

```
问题：
海参有哪些功效？

Retriever 找到：
海马的功效
```

那么 LLM 再聪明也很危险。

所以一个 RAG 系统真正影响效果的，往往并不是：

```
GPT-5
还是
Qwen
```

而是：

```
数据质量
Chunk
Embedding
Retrieval
Reranking
Prompt
```

甚至很多时候：

```
RAG 80% 的工作
不是 LLM
而是数据工程 + 检索工程
```

# 二十三、RAG、Agent 的关系

RAG：

```
LLM
 ↓
Retrieval
 ↓
Knowledge
```

Agent：

```
LLM
 ↓
判断该干什么
 ↓
调用 Tool
```

RAG 本身甚至可以成为 Agent 的一个 Tool：

```
Agent

 ├─ search_papers()
 ├─ rag_search()
 ├─ web_search()
 ├─ calculator()
 └─ database_query()
```

比如论文 Agent：

Agent：

```
1. 搜论文
2. 下载论文
3. 建 RAG
4. 检索方法
5. 比较结果
6. 生成综述
```

所以：

```
RAG
=
知识获取能力

Agent
=
任务规划 + 工具调用能力
```

二者结合非常常见。

# 二十四、GraphRAG

普通 RAG：

```
Document
 ↓
Chunk
 ↓
Embedding
```

但是有些问题涉及：

```
人物关系
公司关系
疾病—药物关系
论文引用关系
```

单纯 Chunk 很难表达。

于是：

```
GraphRAG
```

会构建知识图谱：

```
海参
 │
 ├── 含有 → 蛋白质
 │
 ├── 功效 → 补肾
 │
 ├── 功效 → 健脾
 │
 └── 效方 → 海参汤
               │
               └── 来源 → 本草纲目拾遗
```

查询时：

```
Vector Search
+
Knowledge Graph
+
LLM
```
